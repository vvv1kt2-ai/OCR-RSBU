# Доменные документы

Как инженерные скиллы читают доменную документацию проекта при изучении кода.

## Перед изучением кода прочитать

- **`CONTEXT.md`** в корне проекта — `D:\models\CONTEXT.md`.
- **`docs/adr/`** — ADR по той области, в которой собираетесь работать.

Если этих файлов нет — **продолжать молча**. Не сообщать об их отсутствии и не
предлагать создать заранее. Скилл `/domain-modeling` (доступен через
`/grill-with-docs` и `/improve-codebase-architecture`) создаёт их по мере того, как
термины и решения действительно устоялись.

## Структура файлов

Один контекст (этот проект):

```
D:\models\
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-....md
│   └── 0002-....md
├── docs/agents/
└── pipeline.py, svod.py, ...
```

`CONTEXT-MAP.md` в корне нет — проект одноконтекстный.

**Соседняя папка.** У `D:\data-scraping` (скрапер, отдельный git-репозиторий на
GitHub) свой собственный `CONTEXT.md`. Это **другой** глоссарий: термины оттуда не
переносить в работу по конвейеру извлечения и наоборот. Проект «отчетность РСБУ»
объединяет обе папки, но домен у них разный.

## Использовать словарь глоссария

Когда в выводе называется доменное понятие (в заголовке задачи, в предложении по
рефакторингу, в гипотезе, в имени теста) — использовать термин в том виде, как он
определён в `CONTEXT.md`. Не съезжать на синонимы, которых глоссарий явно избегает
(в `CONTEXT.md` они помечены `_Avoid_:`).

Если нужного понятия в глоссарии нет — это сигнал: либо вы изобретаете язык, которого
в проекте нет (подумайте ещё раз), либо это настоящий пробел (отметьте для
`/domain-modeling`).

## Сообщать о конфликтах с ADR

Если вывод противоречит существующему ADR — сказать об этом прямо, а не перекрывать
молча:

> _Противоречит ADR-0007 (event-sourced orders) — но это стоит переоткрыть, потому что…_
