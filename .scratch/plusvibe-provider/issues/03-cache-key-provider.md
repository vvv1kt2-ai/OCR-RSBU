# 03 — Поставщик входит в ключ кэша

**What to build:** ключ кэша транскриптов начинает различать поставщика. Без этого две
площадки с одним именем модели дают один и тот же ключ, и транскрипт одного поставщика
молча попадает в результат другого — это ровно класс дефекта 4.1, который уже стоил
проекту испорченных данных.

**Blocked by:** 02

**Status:** done

- [x] Метка поставщика входит в имя файла кэша
- [x] Для Polza имя файла **байт-в-байт прежнее** — иначе переключение поставщика
      вызовет повторную транскрипцию всех страниц и повторную оплату около 986 ₽
- [x] Для любого другого поставщика имя файла отличается
- [x] Разные варианты одной модели дают разные ключи (вариант выражается суффиксом
      адреса, поэтому различие обязано получаться само, без отдельного поля)
- [x] Отпечаток PDF по-прежнему входит в ключ: замена файла не наследует старый транскрипт
- [x] Защита «имя документа должно соответствовать открытому PDF» сохранена
- [x] Существующий набор тестов идентичности **расширен**, а не заменён: 33 прежние
      проверки остаются на месте
- [x] Добавлена проверка байтового равенства прежнего и нового ключа для Polza —
      регрессия ловится автоматически
- [x] Прогон документа на Polza не создаёт новых файлов кэша (проверка на живом каталоге)
- [x] Контрольные суммы свода не изменились

**Note for the implementer:** демонстрации на живом прогоне у этой задачи нет — второго
поставщика ещё не существует, поэтому доказательством служат тесты на чистой функции
построения ключа. Платить за вызовы здесь не нужно и не следует.
