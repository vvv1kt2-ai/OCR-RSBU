# Задача агенту: извлечение основных форм бухгалтерской отчетности из PDF (РСБУ, 1 полугодие)

## 1. Цель
Из PDF-файлов бухгалтерской отчетности (РСБУ) извлечь **только три основные формы** и сохранить в JSON для последующего финансового анализа:
- **Бухгалтерский баланс** — форма по ОКУД **0710001**
- **Отчет о финансовых результатах (ОФР)** — форма по ОКУД **0710002**
- **Отчет о движении денежных средств (ОДДС)** — форма по ОКУД **0710005**

Всё остальное (отчет об изменениях капитала 0710003, отчет о целевом использовании 0710006, пояснения, титульный лист) — **пропускать**.

**Приоритет №1 — точность цифр.** Внешний вид таблиц в результате не важен.

## 4. Конвейер обработки

### 4.0. Роутер моделей: кто и когда переключает
Переключение моделей выполняет **оркестратор (Python-скрипт агента)** по детерминированным правилам ниже. LLM никогда не выбирает модель сам; человек не переключает вручную — только утверждает конфиг до запуска и смотрит итоги.

Ключи API — из переменных окружения `POLZA_API_KEY` / `PROVOD_API_KEY`. Оба провайдера OpenAI-совместимые (`/v1/chat/completions`), смена провайдера = смена `base_url` в конфиге.

| Этап | Текстовый слой | Скан | Основная модель | Fallback |
|---|---|---|---|---|
| 0. Классификация файла (текст/скан) | локально, PyMuPDF, без LLM | ← | — | — |
| 1. Детекция «где какие формы» | локально (поиск `0710001`/`0710002`/`0710005` в тексте) | LLM, все страницы в 120 dpi | `gemini-2.5-flash-lite` (polza) | тот же через provod |
| 2. Транскрипция страниц | не нужна (`get_text('words')`) | LLM, только целевые страницы, 200 dpi | `gemini-3.8-flash` (polza) | `gemini-3.5-flash` (provod) |
| 3. Структурирование в JSON | rules-парсер; LLM **только если** checks не сошлись | LLM | `gemini-3.8-flash` | `gemini-3.5-flash` (provod) |
| 4. Эскалация (повтор проблемных страниц) | — | LLM, 300 dpi | `claude-sonnet-5` | `claude-sonnet-5` через provod |

Правила эскалации (кодируются явно в оркестраторе):
1. Проверка `checks` не сошлась по строке S после 2 проходов основной модели → страницы, содержащие S, повторно OCR `claude-sonnet-5` в 300 dpi → объединение → повторная проверка.
2. Пустая транскрипция / невалидный JSON / таймаут ×2 → смена провайдера (polza → provod), та же роль модели.
3. Ошибка API (429/5xx) → retry с backoff 2/8/30 с, затем fallback-модель из таблицы.
4. Файл, не сошедшийся после эскалации → статус `needs_review`, не блокирует остальной конвейер.

Псевдокод оркестратора:

```python
for pdf in files:
    pages = classify(pdf)                    # pymupdf: chars/page, без LLM
    if pages.has_text_layer:
        rows = rule_parser(get_text_words(pages))      # детерминированно
        if not all_checks_pass(rows):
            rows = llm_structure(rows, model='gemini-3.8-flash')
    else:
        page_map = llm_detect(render(pdf, 120), model='gemini-2.5-flash-lite')
        txt = llm_transcribe(render(page_map.targets, 200), model='gemini-3.8-flash')
        rows = llm_structure(txt, model='gemini-3.8-flash')
    res = checks(rows)
    if res.failed:
        res = escalate(res, model='claude-sonnet-5', dpi=300)   # только проблемные страницы
    save(json(res))
```

На пилоте выполняется ровно этот же код на 2 файлах. Цели пилота: (а) классификатор правильно разнес файлы по конвейерам; (б) на скане детекция нашла все 3 формы; (в) checks сошлись (или эскалация сработала как задумано); (г) зафиксированы фактические стоимость и время на файл. Параметры (dpi, число ретраев, порог текстового слоя) — константы конфига; пилот их валидирует.

### 4.1. Определение страниц с формами
Формы ищутся по признакам (в тексте или через OCR):
- `0710001` / заголовок «Бухгалтерский баланс»;
- `0710002` / заголовок «Отчет о финансовых результатах»;
- `0710005` / заголовок «Отчет о движении денежных средств».
Форма занимает 2–3 страницы: продолжения помечены «Форма 0710001 с. 2» и т.п. Пример карты страниц (файл «Рекорд трейд_6мес_2026.pdf»): стр. 1–3 баланс, 4–5 ОФР, 6–8 ОИК (пропустить), 9–11 ОДДС, 12+ пояснения (пропустить).
Для сканов: сначала прогнать детекцию заголовков на всех страницах (дешевой моделью, например `gemini-2.5-flash-lite`), затем целевые страницы — основной моделью.

### 4.2. Извлечение
- **Текстовый слой:** `page.get_text()`; если колонки считываются вразнобой — использовать `get_text('words')` с координатами и восстанавливать строки по Y.
- **Сканы:** PNG 200 dpi → vision-модель с промптом «распознать таблицу дословно, сохранив все числа как напечатаны» → структурирование в JSON.
- Структурирование в JSON — LLM с низким temperature (0–0.2) и явной схемой.

### 4.3. Правила чтения значений (критично для точности)
- Разделители тысяч (`12 112`) — игнорировать; десятичный разделитель — запятая или точка как напечатано.
- `-` / `–` / пустая ячейка = **null** (не 0).
- Число в скобках `(1 345)` = **отрицательное**.
- Единица измерения — из шапки формы (поле «Единица измерения», обычно «тыс. руб.» по ОКЕИ 384; бывает «млн руб.» 385 или «руб.» 383). **Хранить в JSON как есть; не пересчитывать.**
- У баланса 3 колонки дат (например: на 30.06.2026, на 31.12.2025, на 31.12.2024); у ОФР и ОДДС 2 колонки периодов (за 1 полугодие 2026 и за 1 полугодие 2025). Даты брать из шапки, а не предполагать.
- Строки «в том числе» хранить как дочерние элементы — **не смешивать с итогами**.
- Если в файле упрощенные формы (малое число строк) — коды строк могут отсутствовать; сопоставлять по названиям показателей из эталонного списка (п. 6), поле `code` может быть null.

## 7. Контроль качества и верификация
1. **Арифметика** (раздел `checks`) — обязательна по каждой колонке каждой формы.
2. **Верификационный проход:** для каждого файла повторно распознать (или перечитать) 2–3 случайные строки + все строки, где проверка не сошлась; сканы с расхождениями — повторный OCR в 300 dpi более сильной моделью (`claude-sonnet-5`).
3. Файлы, где баланс не сходится после повторной проверки — не отбрасывать, а помечать `"status": "needs_review"` с перечнем проблемных строк в `warnings`.
4. Семплирование: не менее 5% файлов проверить человеком по оригиналу — включить в итоговый отчет список проверенных.
