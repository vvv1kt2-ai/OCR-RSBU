## 2. Что сделано хорошо (без иронии)

Это заметно выше среднего уровня самодельного конвейера, и это важно сказать до списка ошибок.

1. **Провенанс.** Ключ кэша страницы = документ + страница + dpi + модель + **sha1 байтов PDF** + поставщик. Дефект 4.1 («баланс Корпсана попал в ТГК-14») закрыт именно этим, а не заплаткой.
2. **Правила арифметики как приёмка, а не как украшение.** Форма, не сходящаяся по тождествам, честно помечается; из этого выросли и находка обрезки `content_filter`, и потеря строки 1520.
3. **Гейт эскалации** (`escalation_gate`, `pipeline.py:390`) с четырьмя критериями, включая невязку по клеткам, вычислимым **в обеих** редакциях — это ровно та проверка, которой не хватало, чтобы поймать порчу `1250` у ТГК-14.
4. **Отделение «не знаю» от «не форма»** (`unknown` vs `other`, `pipeline.py:1704`) — редкая аккуратность в проектировании разметки.
5. **Документирование отозванных выводов.** `_ИНДЕКС.md` содержит раздел «файлам, которым нельзя верить целиком». Это признак честной работы, а не слабость.
6. **Кэш как деньги.** Осознание, что транскрипт — платный актив, и что метка поставщика обязана входить в имя файла, иначе «одна страница, два числа».

## 3. Ошибки (найдены, воспроизведены)

### 3.1. ГЛАВНАЯ (в исправленной редакции): артефакты невоспроизводимы

**Что было сказано сначала и почему это неверно.** Первый замер показал, что правило
`1500 == 1510+1520+1530+1540+1550` проваливается на 17 из 43 балансов, и в 15 случаях
невязка в точности равнялась значению дочерней строки «Обязательство по аренде» внутри 1520.
Вывод «правило не знает про аренду, а свод знает» был поспешным.

**Проверка на текущем коде.** Тот же оплаченный ответ модели (`_llm_Бианка премиум_6мес_2025_
tstruct_balance_p1_2_3_4_pv.json`), прогнанный через текущие `_normalize_llm` и `run_checks`:

```
1520 = 305152   (merge_duplicate_codes сложил «Кредиторская задолженность» 122436
                 и «Обязательство по аренде» 182716 — обе строки пришли с кодом 1520)
1600 == 1700                       ok
1100 == 1110+1120+…+1190           ok
1200 == 1210+1215+…+1260           ok
1300+1400+1500 == 1700             ok
1400 == 1410+1420+1430+1440+1450   ok
1500 == 1510+1520+1530+1540+1550   ok      <- в артефакте было False
```

Правило верно. Артефакт — нет.

**Что подтвердилось и оказалось важнее.** Прогон всех 43 артефактов против их оплаченных
кэшей (пара «артефакт ↔ кэш» подтверждается совпадением набора верхнеуровневых кодов):

| Замер | Число |
|---|---|
| Форм с подтверждённой парой «артефакт ↔ кэш» | 73 |
| Форм, которые из кэша не воспроизводятся | 16 |
| Провалов правил в артефактах | 24 |
| Провалов правил на текущем коде (те же документы) | 9 |
| Расхождений «значение в артефакте ≠ оплаченный ответ модели» | 16 |

Направление изменений почти всегда `False → True`, то есть текущий код **чинит** то, что
артефакт показывает как провал. Единственное исключение — `Славянск ЭКО_6мес_2025`, и оно
показательно: в артефакте `1240 = [None, None, 2942100]`, а в ответе модели
`1240 = [2942100, None, None]` — значение **сдвинуто на колонку влево**. Артефакт исправлен
руками, ответ модели нет. Правило `1200` падает на обоих, но по разным причинам.

**Что это значит.** В `extracted/` смешаны три вещи, различить которые сейчас нечем:
1. вывод прежних версий кода;
2. ручные правки — не менее 5 исправленных цифр (`Славянск ЭКО_6мес_2026` 1260: 175 → 177;
   2340: 25 614 121 → 25 814 121; 4110: 171 708 220 → 171 706 220; `ТГК-14_6мес_2025` 1100
   кол.2: …198 → …188) и минимум один сдвиг колонки;
3. отсутствие записи о том, из какого кэша артефакт сделан: `source.method` нет ни у одного
   из 43.

Поэтому «пересчитать status из items» — необходимое, но недостаточное действие: оно даёт
верный вердикт для ДАННЫХ КАК ОНИ ЛЕЖАТ, но не отвечает на вопрос «а верны ли сами цифры».
И ручные правки — это единственная существующая запись о том, где модель прочитала неверно;
пока они не выделены в отдельный слой, их нельзя ни посчитать, ни защитить от потери.

**Что сделано.** `_verify_artifacts.py` (см. конец отчёта) делит невязки на два класса:

```
артефактов: 43
провалов правил (правило x документ): 28
невязок по колонкам: 48
  объяснено разбором (строка вне итога): 44
  ПОДОЗРЕНИЕ НА ЧТЕНИЕ: 4
```

Все четыре подозрения на чтение: `ИПС_6мес_2025` (три колонки — та самая потерянная строка
1520 = 15307 из `_ДЕТЕКЦИЯ_ПОЛНОТА.md`) и `Корпсан_6мес_2026` кол.0. Это и есть настоящий
список того, что стоит перечитать, — вместо 17 ложных.

**Что делать дальше (не сделано, требует решения).** Ручные правки должны стать отдельным
слоем (`corrections.json`: документ, форма, код, колонка, прежнее значение, новое, причина),
а артефакт — результатом «вывод кода + слой правок». Тогда артефакт воспроизводится, правки
не теряются, и появляется метрика доли неверно прочитанных цифр — то, ради чего правила и
существуют.

### 3.2. «Невычислимо» записывается как «провал» — **ИСПРАВЛЕНО**

`pipeline.py:619`:
```python
ok = all(v is not False for v in per_col) and any(v is True for v in per_col)
```
Если правило не вычислимо ни в одной колонке (`per_column == [None]`), `any(v is True)` = False → **`ok=False`**, то есть провал. Это прямо противоречит замыслу того же кода: `sect()` (`pipeline.py:559`) и все лямбды возвращают `None` именно для того, чтобы «нет детализации» **не** стало ложным провалом (комментарий `pipeline.py:577-581`).

Воспроизведение на синтетическом входе — баланс, который сходится, но без детализации разделов:

```
True   per_column=[True]   1600 == 1700
False  per_column=[None]   1100 == 1110+1120+...
False  per_column=[None]   1200 == 1210+1215+...
True   per_column=[True]   1300+1400+1500 == 1700
False  per_column=[None]   1400 == 1410+1420+1430+1440+1450
False  per_column=[None]   1500 == 1510+1520+1530+1540+1550
```

4 правила из 6 объявлены провалом при полностью корректных данных.

Второе следствие: форма без колонок (`n == 0` → `per_column == []`) тоже даёт `ok=False`. Именно так выглядят 9 сохранённых проверок у ИПС / Йуми / Селл-Сервис.

**Что делать.** Ввести три исхода вместо двух: `ok / fail / n/a`. В приёмку идут только `fail`; `n/a` попадает в предупреждения, но не в `needs_review` и не в эскалацию.

### 3.3. Эскалация не может править расходные строки ОФР/ОДДС — **ИСПРАВЛЕНО**

`pipeline.py:1238`:
```python
for tok in re.findall(r'(?<![\d-])\d{4}(?![\d-])', c['rule']):
```
Запрет на цифру **или минус** слева/справа отсекает коды, стоящие рядом со знаком. Замер по всем строкам правил:

| Правило | Коды, которые попадают в `want` | Потеряно |
|---|---|---|
| `2100 == 2110-2120 (±)` | `{2100}` | 2110, 2120 |
| `2200 == 2100-2210-2220 (±)` | `{2200}` | 2100, 2210, 2220 |
| `2400 == 2300-2410±2421∓2430±2450-2460` | `{2400, 2421, 2430}` | 2300, 2410, 2450, 2460 |

`want` — это список кодов, которые эскалации **разрешено** перезаписать (`pipeline.py:1319`). То есть для ОФР эскалации разрешено править только итоговые строки и **запрещено** — ровно те, где чаще всего теряется знак или скобка (2120, 2210, 2220, 2410, 2460). Для баланса и ОДДС баг не проявляется (там знаки не в строке правила).

**Что делать.** Разбирать правило на токены, а не вылавливать числа регуляркой: `re.findall(r'\d{4}', rule)` (внутри правила нет чисел длиннее 4 цифр) либо явный список кодов рядом с текстом правила.

### 3.4. Мёртвый код в ветке «эскалация не изменила ничего» — **ИСПРАВЛЕНО**

`pipeline.py:1356-1358`:
```python
else:
    res['checks'] = [dict(form=form_key, **c) for c in run_checks(form_key, res['items'])
                     if False] or [c for c in result['checks'] if c['form'] == form_key]
```
`if False` делает генератор всегда пустым, работает только правая часть `or`. Условие `if False` в продакшене — признак незакрытой правки; читателю он не сообщает ничего, а `run_checks` вызывается впустую.

### 3.5. Артефакты и свод заморожены и разошлись с кодом

> Полный разбор — в переписанном 3.1 (там же замер «24 провала в артефактах против 9 на
> текущем коде» и найденные ручные правки). Ниже — то, что видно без обращения к кэшу.

Три независимых замера:

1. **13 из 43 артефактов** имеют `status`, противоречащий пересчёту из их же `items`:
   - 12 стоят `ok`, а по текущим правилам дают `needs_review` (Бианка премиум ×2, ИПС_2025, КИФА_2026, Органик парк_2026, Проект 111 ×2, Простая еда_2025, Сибсульфур ×2, Смартфакт_2026, Эфферон_2026);
   - 1 стоит `needs_review` (Селл-Сервис_2026), а все проверки сходятся.
2. **9 сохранённых `checks` устарели** — пересчёт даёт `ok=True` там, где сохранено `False` (ИПС/Йуми/Селл-Сервис, ОФР).
3. **`source.method` отсутствует во всех 43 артефактах**, хотя код пишет его всегда (`pipeline.py:1975`, `2120`, `2155`). То есть ни один артефакт в `extracted/` не порождён текущей версией кода.

Плюс `Простая еда_6мес_2025`: правка `BAL_NAMES['доходыбудущихпериодов'] = ['1530']` (комментарий `pipeline.py:676-678`) в артефакте не отражена — «Доходы будущих периодов» = 2335 остались ребёнком **без кода** внутри 1520.

**Почему это важно, а не косметика.** `status` — это то, по чему человек решает, доверять ли числу. Сейчас `status=ok` у ИПС_6мес_2025 стоит на документе с потерянной строкой 1520 = 15307 (та самая потеря из `_ДЕТЕКЦИЯ_ПОЛНОТА.md`). И 12 документов с `ok` сегодня не проходят собственные правила проекта.

**Что делать.** (1) `checks` и `status` — производные, а не хранимые: считать их при чтении артефакта, а в JSON держать только `items`. (2) Отдельный скрипт `_verify_artifacts.py`, который пересчитывает статус по всем артефактам и печатает расхождения — он бесплатный (модели не зовутся) и должен идти перед любой сборкой свода.

### 3.8. Мелкие, но реальные

- **Гонка в учёте стоимости.** `USAGE['calls'] += 1`, `USAGE['prompt'] += pt` (`pipeline.py:112-113`) выполняются из 4 потоков (`ThreadPoolExecutor(max_workers=4)`, `pipeline.py:1895`, `1772`). `+=` по элементу словаря не атомарен → потерянные обновления → **заниженная** стоимость прогона. А стоимость — это то, на чём принимаются решения об эскалации.
- **Побочный эффект при импорте.** `KEY = load_key()` (`pipeline.py:72`) на уровне модуля: `import pipeline` падает без файла `C:\Users\1\.dsh\.credentials.yaml`. Тесты и любой анализ данных вынуждены иметь боевой ключ.
- **Глобальное состояние.** `doc_result` — модульная переменная, которую `scan_pipeline` наполняет, а `process` чистит (`pipeline.py:1960`, `2218`, `2242`). Пока документы обрабатываются по одному, это работает; распараллелить обработку документов нельзя без переписывания. Комментарии в коде признают эту связанность («doc_result (global, filled by scan_pipeline)»), но не устраняют.
- **`cached_transcript_path`** (`pipeline.py:1516`) делает `os.listdir` по каталогу из 2982 файлов на **каждую** страницу. При росте корпуса это O(страницы × файлы).

### 3.9. `data-scraping`

- **Нет проверки содержимого при скачивании.** `_download_file` (`scraper.py:321`) пишет `response.body()` при `response.ok`. Если сайт отдаёт HTML-страницу капчи с кодом 200, она сохранится как `.zip` и «успешно» распакуется в ноль PDF. Проверки магических байтов (`PK`, `Rar!`) нет.
- **`pick_largest_pdf`** (`unpack.py:59`) — эвристика «самый большой PDF = отчёт». В `CONTEXT.md` уже зафиксирован случай «Энерготехсервис — 5 PDF, выбран самый большой». Молчаливый выбор из нескольких кандидатов — источник трудноуловимых подмен; минимум нужен признак «выбрано N из M» в лог и в имя файла.
- **Тесты не версионируются.** `.gitignore:26-27` игнорирует `tests/` и `src/`. В `data-scraping` есть `tests/` — он не попадёт в репозиторий. В `models` тесты, наоборот, версионируются. Две политики на два проекта.
- **Задержка не соблюдается внутри компании.** `_delay()` вызывается только между компаниями (`scraper.py:576`), а между скачиванием 2026 и 2025 годов (`scraper.py:584-588`) — нет, хотя каждое это полная навигация. Это же удваивает нагрузку: страница компании открывается заново и в фазе 2 (3 навигации на компанию вместо 1).
- **Гигиена.** `_vision_secret.txt` (содержимое `U8U6R2`) — **отслеживается git и не в `.gitignore`**. Это тестовая строка-фикстура для проверки зрения модели, а не боевой ключ, но файл с именем «secret» в истории репозитория — плохой прецедент, и он показывает, что `.gitignore` не покрывает `_vision_*` целиком.

### Слой правок (`corrections.json`)

Отдельный файл в корне `D:\models` (вне `extracted/`, поэтому **попадает в git**). Артефакты
остаются чистым выводом кода, рука живёт отдельно.

- **Ключ** `(doc, form, column, code)` не содержит ни списка отчётностей, ни списка кодов свода —
  правки переживают перестройку обоих. Записи про коды, выпавшие из свода, не теряются.
- **Запись не перезаписывается**: новое состояние дописывается в `history`, поэтому
  `git log -p corrections.json` показывает, когда пометка появилась и чем закончилась.
- **Правка по конкретному коду перебивает пометку про колонку** — иначе проверенную ячейку
  нельзя было бы закрыть отдельно от остальных.
- **Состояния:** `disputed` (сиреневая заливка), `corrected` (зелёная), `confirmed` / `rejected`
  (закрытые, заливки нет).
- Помечается и **пустая** ячейка: у `ИПС` пропущена строка `1550`, и в своде она теперь видна
  как «— не прочитано —». Без этого пропуск был бы неотличим от «данных нет».
- Правка, которой некуда лечь (строки с таким кодом в форме нет), **не применяется и не создаёт
  строку** — выводится предупреждение. Записывать прочитанное значение в несуществующую строку
  нельзя: она не была прочитана.
